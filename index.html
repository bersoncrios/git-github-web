DIFERENÇA ESSENCIAL

Git ≠ GitHub

Ferramenta de versionamento versus plataforma de hospedagem e colaboração.

⌘

Git · mecanismo

Sistema de controle de versões distribuído. Gerencia commits, branches, merges e histórico, inclusive sem internet.

↗

GitHub · plataforma

Hospeda repositórios Git e oferece pull requests, issues, reviews, permissões e automações.

VS
Você pode usar Git sem GitHub; GitHub é uma das plataformas possíveis para colaboração sobre repositórios Git.
Uma analogia útil: Git é o motor de versionamento; GitHub oferece infraestrutura e uma interface social/colaborativa. GitLab e Bitbucket são alternativas.

COMEÇANDO

Primeiro, configure sua identidade

Os campos de autoria aparecem no histórico dos commits.

TERMINAL / bash 
git --version
                  git config --global user.name "Seu Nome"
                  git config --global user.email "voce@exemplo.com"
                  git config --global --list
Importante: nome e e-mail configurados são metadados do commit; não são, por si só, suas credenciais de autenticação no GitHub.
Explique --global versus --local. Verifique se o terminal reconhece git. No GitHub, autenticação HTTPS pode usar credential manager/token, ou SSH com chave configurada.
REPOSITÓRIO

Da pasta ao repositório Git

git init cria a estrutura de versionamento na pasta atual.

TERMINAL / bash 
mkdir minha-aplicacao
                      cd minha-aplicacao
                      git init -b main
                      echo "# Minha aplicação" > README.md

.git/ = dados do repositórioREADME.md = documentaçãomain = branch inicial
Mostre a diferença entre arquivo normal de projeto e metadados ocultos no diretório .git. “git init -b main” depende de versão compatível do Git.

DEMONSTRAÇÃO

Seu primeiro commit

Um commit registra um snapshot do que foi preparado.

TERMINAL / bash 
git status
                                  git add README.md
                                  git diff --staged
                                  git commit -m "docs: adiciona README inicial"
                                  git log --oneline
Sequência: inspecionar → preparar → revisar → registrar → conferir histórico.
Após o add, o diff --staged confirma o conteúdo do próximo commit. Git commit não publica no GitHub. O hash é um identificador do objeto commit.
CONTROLE

Enxergue o histórico

Não trabalhe às cegas: confira o estado e compare alterações.

TERMINAL / bash 
git status
                                      git log --oneline --graph --decorate
                                      git diff
                                      git diff --staged
                                      git show HEAD
diff → alterações não preparadasdiff --staged → alterações preparadaslog → histórico
Explique a diferença entre diff e diff --staged. git show HEAD exibe detalhes do commit atualmente apontado por HEAD.
BOAS PRÁTICAS

Um bom commit conta uma história

Faça alterações pequenas, coesas e com mensagens que expressem intenção.

✓

Mensagens claras

feat: adiciona validação de e-mail
fix: corrige cálculo do frete
docs: atualiza instruções

×

Mensagens fracas

ajustes
coisas
subi tudo
agora vai final

Convenções como Conventional Commits são opcionais, mas ajudam na consistência e na automação de releases.
Não apresente Conventional Commits como obrigação do Git: é uma convenção de mensagens. Prefira mensagem imperativa, escopo e intenção claros.
REMOTO

Seu código no GitHub

Crie primeiro um repositório vazio no GitHub e conecte-o ao repositório local.

TERMINAL / bash 
# No GitHub: crie um repositório VAZIO
                                          git remote add origin https://github.com/USUARIO/minha-aplicacao.git
                                          git push -u origin main
                                          git remote -v
origin é o nome do remoto. -u configura a relação de acompanhamento (upstream) da branch, facilitando comandos futuros.
A URL é um exemplo; substitua USUARIO. Para evitar histórico divergente no primeiro push, não marque a opção de criar README no remoto se você já o criou localmente.
SINCRONIZAÇÃO

Clone, fetch, pull e push

Quatro operações comuns, mas com responsabilidades diferentes.

TERMINAL / bash 
git clone https://github.com/USUARIO/minha-aplicacao.git
                                              git fetch origin       # busca objetos e referências
                                              git pull origin main    # busca e integra alterações
                                              git push origin main    # envia commits locais
git fetch atualiza referências remotas sem integrar automaticamente na branch atual. git pull busca e integra (merge ou rebase, conforme configuração).
Esclareça que pull pode fazer merge ou rebase conforme a configuração; não é sempre um merge tradicional. Diferencie clone de download ZIP (que não contém o histórico Git).
BRANCHING

Branches: evoluir sem interromper

Uma branch é uma referência móvel para uma sequência de commits.

Cada círculo representa um commit. Branches são referências móveis para commits.
Trabalhar em feature/login não altera main até que as mudanças sejam integradas.
Tecnicamente branch é uma referência móvel para commit; a estrutura do histórico permite múltiplas linhas de desenvolvimento. O diagrama mostra uma integração conceitual.
BRANCHING

Uma funcionalidade, uma branch

Isole a mudança, desenvolva, faça commit e publique a branch.

TERMINAL / bash 
git switch -c feature/pagina-login
                                                  # Edite os arquivos do projeto
                                                  git status
                                                  git add .
                                                  git commit -m "feat: cria tela de login"
                                                  git push -u origin feature/pagina-login
git switch -c → cria + mudagit switch main → retornagit branch → lista
Em uma demonstração real, é melhor usar git add com caminhos explícitos se houver arquivos não intencionais no diretório. git switch é o comando moderno; checkout também pode ser encontrado em tutoriais antigos.
INTEGRAÇÃO

Merge: reunir trabalhos

O Git integra históricos de desenvolvimento de duas branches.

TERMINAL / bash 
git switch main
                                                      git pull origin main
                                                      git merge feature/pagina-login
                                                      git log --oneline --graph
                                                      git push origin main
Em equipes, normalmente a integração acontece após um pull request revisado, e não por merge direto da máquina de cada desenvolvedor.
Distinga fast-forward de merge commit, se houver tempo. Política de branches protegidas pode impedir push direto na main.
MERGE CONFLICT

Quando o Git precisa de você

Conflitos exigem uma decisão humana sobre qual deve ser o conteúdo final.

TERMINAL / conflito / exemplo 
<<<<<<< HEAD
                                                          <h1>Bem-vindo!</h1>
                                                          =======
                                                          <h1>Olá, equipe!</h1>
                                                          >>>>>>> feature/cabecalho
                                                          # Edite o arquivo removendo os marcadores
                                                          git add index.html
                                                          git commit
Conflito não significa erro fatal. Resolva o conteúdo, execute os testes e conclua a integração.
Esclareça que marcadores <<<<<<<,=======e>>>>>>> são inseridos pelo Git durante certos conflitos. Você decide e edita o arquivo. Em caso de merge ainda em andamento, git commit finaliza, ou git merge --continue.
COLABORAÇÃO

GitHub Flow: do código à revisão

Um fluxo simples e popular para entregar mudanças em equipe.

01 / CRIARBranchSeparar mudança
→
02 / CODIFICARCommitsImplementar e testar
→
03 / PROPORPull requestRevisar e discutir
→
04 / INTEGRARMergeUnir à main
Após o merge: excluir a branch de trabalho (quando apropriado) e atualizar a main local.
GitHub Flow pressupõe uma branch principal protegida e branches curtas para mudanças. Pull request permite discussão, revisão e checagens automáticas.
CONCEITO-CHAVE

git pull ≠ pull request

Nomes parecidos, operações totalmente diferentes.

↓

git pull

Comando Git. Busca alterações remotas e as integra à branch local, usando a estratégia configurada.

↗

Pull request

Recurso do GitHub. Propõe mesclar mudanças entre branches, permitindo revisão, comentários e testes.

≠
Pergunta comum em entrevistas e equipes: “Abrir um PR” não é executar git pull.
Reforce com exemplos: pull = atualizar sua cópia; PR = pedir discussão e integração da sua mudança.
PASSO A PASSO

Seu primeiro pull request

O PR explica o que mudou, por que mudou e como verificar.

↑

01 · Publique

Faça git push da branch para o GitHub.

≠

02 · Compare

No GitHub: Compare & pull request. Base: main; compare: sua branch.

✓

03 · Revise

Escreva título, contexto, testes; peça revisão e incorpore feedback.

Merge: após as aprovações e verificações necessárias, integre a branch pela interface do GitHub.
Na interface, base é a branch de destino e compare é a branch que contém as mudanças. Demonstre arquivos alterados e aba de revisão. Se possível, mostre PR de exemplo.
QUALIDADE

Code review é engenharia em equipe

Uma boa revisão melhora comportamento, clareza, segurança e manutenção.

↑

Quem abre o PR

Contextualiza a mudança, mostra como testar, mantém escopo claro e responde ao feedback.

◎

Quem revisa

Confere lógica, legibilidade, efeitos colaterais, testes e riscos; sugere melhorias específicas.

Issues → tarefas e bugsReviews → colaboraçãoChecks → integração contínua
Code review não é punição nem apenas estilo; avalia riscos e contribui para conhecimento compartilhado. CI é opcional mas muito comum.
CUIDADO

Desfazer sem apagar a história

Escolha o comando conforme o estado da alteração.

TERMINAL / bash 
git restore arquivo.txt          # descarta edição local
                                                                git restore --staged arquivo.txt  # retira do stage
                                                                git revert HASH                  # novo commit de reversão
                                                                # CUIDADO: git reset --hard pode eliminar mudanças locais
Regra de ouro: em um histórico compartilhado, prefira git revert para desfazer um commit publicado sem reescrever o histórico.
restore é destrutivo para alterações locais não salvas em commit. revert cria novo commit inverso. Não recomendar reset --hard sem explicar perda de dados. Evitar force push na main.
BOAS PRÁTICAS

Repositório saudável e seguro

Estrutura, documentação e cuidado com informações sensíveis.

▤

README.md

Objetivo, instalação, execução, testes e contribuição.

⊘

.gitignore

Ignora arquivos gerados, dependências locais e configurações não versionáveis.

⚠

Segredos

Nunca commitar senhas, tokens ou chaves; use secrets e variáveis de ambiente.

Se um segredo foi commitado, removê-lo do arquivo não basta: revogue ou rotacione a credencial exposta.
Importante: gitignore impede novos arquivos não rastreados de serem adicionados por padrão; não remove arquivos já rastreados. Ao vazar segredo, revogue primeiro, depois avalie limpeza do histórico.

COMANDOS / PARTE B

Branch + commit + PR

Agora faça uma alteração isolada para propor à branch principal.

TERMINAL / bash 
git switch -c feature/descricao
                                                                        echo "Projeto de demonstração do Git." >> README.md
                                                                        git add README.md
                                                                        git commit -m "docs: descreve projeto"
                                                                        git push -u origin feature/descricao
                                                                        # No GitHub: Compare & pull request
                                                                        # Base: main / compare: feature/descricao
Pergunte: “O que aconteceu com a main antes de clicar em merge?” Ela permaneceu inalterada.
Lembre a distinção entre enviar a branch e mesclá-la. Se houver tempo, peça a alguém para revisar o PR e demonstrar a aba Files changed.
