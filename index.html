Sistema de controle de versões distribuído. Gerencia commits, branches, merges e histórico, inclusive sem internet.

↗

DEMONSTRAÇÃO

Seu primeiro commit

Um commit registra um snapshot do que foi preparado.

TERMINAL / bash 
git status
                                  git add README.md
                                  git diff --staged
                                  git commit -m "docs: adiciona README inicial"
                                  git log --oneline
Sequência: inspecionar → preparar → revisar → registrar → conferir histórico.
Após o add, o diff --staged confirma o conteúdo do próximo commit. Git commit não publica no GitHub. O hash é um identificador do objeto commit.
CONTROLE

Enxergue o histórico

Não trabalhe às cegas: confira o estado e compare alterações.

TERMINAL / bash 
git status
                                      git log --oneline --graph --decorate
                                      git diff
                                      git diff --staged
                                      git show HEAD
diff → alterações não preparadasdiff --staged → alterações preparadaslog → histórico
Explique a diferença entre diff e diff --staged. git show HEAD exibe detalhes do commit atualmente apontado por HEAD.

REMOTO

Seu código no GitHub

Crie primeiro um repositório vazio no GitHub e conecte-o ao repositório local.

TERMINAL / bash 
# No GitHub: crie um repositório VAZIO
                                          git remote add origin https://github.com/USUARIO/minha-aplicacao.git
                                          git push -u origin main
                                          git remote -v
origin é o nome do remoto. -u configura a relação de acompanhamento (upstream) da branch, facilitando comandos futuros.
A URL é um exemplo; substitua USUARIO. Para evitar histórico divergente no primeiro push, não marque a opção de criar README no remoto se você já o criou localmente.
SINCRONIZAÇÃO

Clone, fetch, pull e push

Quatro operações comuns, mas com responsabilidades diferentes.

TERMINAL / bash 
git clone https://github.com/USUARIO/minha-aplicacao.git
                                              git fetch origin       # busca objetos e referências
                                              git pull origin main    # busca e integra alterações
                                              git push origin main    # envia commits locais
git fetch atualiza referências remotas sem integrar automaticamente na branch atual. git pull busca e integra (merge ou rebase, conforme configuração).
Esclareça que pull pode fazer merge ou rebase conforme a configuração; não é sempre um merge tradicional. Diferencie clone de download ZIP (que não contém o histórico Git).
BRANCHING

Branches: evoluir sem interromper

Uma branch é uma referência móvel para uma sequência de commits.

Cada círculo representa um commit. Branches são referências móveis para commits.
Trabalhar em feature/login não altera main até que as mudanças sejam integradas.
Tecnicamente branch é uma referência móvel para commit; a estrutura do histórico permite múltiplas linhas de desenvolvimento. O diagrama mostra uma integração conceitual.
BRANCHING

Uma funcionalidade, uma branch

Isole a mudança, desenvolva, faça commit e publique a branch.

TERMINAL / bash 
git switch -c feature/pagina-login
                                                  # Edite os arquivos do projeto
                                                  git status
                                                  git add .
                                                  git commit -m "feat: cria tela de login"
                                                  git push -u origin feature/pagina-login
git switch -c → cria + mudagit switch main → retornagit branch → lista
Em uma demonstração real, é melhor usar git add com caminhos explícitos se houver arquivos não intencionais no diretório. git switch é o comando moderno; checkout também pode ser encontrado em tutoriais antigos.
INTEGRAÇÃO

Merge: reunir trabalhos

O Git integra históricos de desenvolvimento de duas branches.

TERMINAL / bash 
git switch main
                                                      git pull origin main
                                                      git merge feature/pagina-login
                                                      git log --oneline --graph
                                                      git push origin main
Em equipes, normalmente a integração acontece após um pull request revisado, e não por merge direto da máquina de cada desenvolvedor.
Distinga fast-forward de merge commit, se houver tempo. Política de branches protegidas pode impedir push direto na main.
MERGE CONFLICT

Quando o Git precisa de você

Conflitos exigem uma decisão humana sobre qual deve ser o conteúdo final.

TERMINAL / conflito / exemplo 
<<<<<<< HEAD
                                                          <h1>Bem-vindo!</h1>
                                                          =======
                                                          <h1>Olá, equipe!</h1>
                                                          >>>>>>> feature/cabecalho
                                                          # Edite o arquivo removendo os marcadores
                                                          git add index.html
                                                          git commit
Conflito não significa erro fatal. Resolva o conteúdo, execute os testes e conclua a integração.
Esclareça que marcadores <<<<<<<,=======e>>>>>>> são inseridos pelo Git durante certos conflitos. Você decide e edita o arquivo. Em caso de merge ainda em andamento, git commit finaliza, ou git merge --continue.

CONCEITO-CHAVE

git pull ≠ pull request

Nomes parecidos, operações totalmente diferentes.

↓

git pull

Comando Git. Busca alterações remotas e as integra à branch local, usando a estratégia configurada.

↗

Pull request

Recurso do GitHub. Propõe mesclar mudanças entre branches, permitindo revisão, comentários e testes.

≠
Pergunta comum em entrevistas e equipes: “Abrir um PR” não é executar git pull.
Reforce com exemplos: pull = atualizar sua cópia; PR = pedir discussão e integração da sua mudança.

GIT NO MERCADO

Estratégias de branches no mercado

Não existe um único fluxo obrigatório: o processo acompanha o produto e a frequência de entrega.

⑂

GitHub Flow

Uma main estável e branches curtas com PRs; adequado a entregas contínuas.

⇄

GitFlow

Pode usar develop, feature, release e hotfix; mais etapas e branches de longa duração.

∞

Trunk-based

Integrações frequentes em uma trunk; branches muito curtas e automação de testes.

Qual usar? Prefira o fluxo mais simples que cumpra as necessidades de revisão, testes, estabilidade e implantação do seu time.
Evite afirmar que toda empresa usa GitFlow. Em entregas contínuas, equipes frequentemente preferem branches curtas. Se usar feature flags, explique que mudanças incompletas podem ser integradas sem ficarem visíveis ao usuário.

Desafio de equipe: decida o fluxo

Situação: uma funcionalidade está pronta, mas a main recebeu alterações de outros desenvolvedores.

CASO PRÁTICO / DISCUSSÃO

Você é responsável pela tarefa APP-142

Seu PR falhou em um teste e há conflito no arquivo de rotas. O deploy de hoje depende da estabilidade da main. O que você faz?

01

Investigar

Consultar o resultado do CI e reproduzir a falha localmente.

02

Sincronizar

Atualizar a branch com a base, resolver conflitos e executar testes.

03

Revalidar

Publicar as correções, responder ao review e aguardar os checks exigidos.

Mensagem central: não faça merge apenas para “destravar” o pipeline. Integração é responsabilidade compartilhada.
Use 60 segundos de discussão com a plateia. Uma solução possível é git fetch origin e git merge origin/main enquanto estiver na feature branch; em outras equipes pode-se usar rebase com cuidado, especialmente se a branch é compartilhada. Não forçar push em main.
CUIDADO

Desfazer sem apagar a história

Escolha o comando conforme o estado da alteração.

TERMINAL / bash 
git restore arquivo.txt          # descarta edição local
                                                                git restore --staged arquivo.txt  # retira do stage
                                                                git revert HASH                  # novo commit de reversão
                                                                # CUIDADO: git reset --hard pode eliminar mudanças locais
Regra de ouro: em um histórico compartilhado, prefira git revert para desfazer um commit publicado sem reescrever o histórico.
restore é destrutivo para alterações locais não salvas em commit. revert cria novo commit inverso. Não recomendar reset --hard sem explicar perda de dados. Evitar force push na main.

FECHAMENTO

Checklist para um time produtivo

Uma rotina simples reduz conflitos e aumenta previsibilidade.

01

Antes

Sincronize a branch de trabalho e entenda o objetivo da tarefa.

02

Durante

Mudanças pequenas, git status, diff e commits descritivos.

03

Ao enviar

Push da branch, PR explicativo, testes e solicitação de review.

04

Depois

Integre a alteração, atualize a main e limpe branches obsoletas.

Reforce: Git organiza o histórico, mas a qualidade da colaboração depende das rotinas e acordos do time.
